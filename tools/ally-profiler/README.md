# Ally profiler

Standard-library Python 3.9+ tools for read-only AMD GPU and Linux process/thread telemetry, plus MangoHud CSV analysis. No dependencies to install. The tool never launches a process, attaches a debugger, reads process memory, captures images/shaders, changes settings, or uploads anything. It does not modify Steam shortcuts or Proton prefixes.

## Safety and output

Run from the source checkout. All persistent tool output goes into unique timestamped directories under **`~/nhl-ally-profiles/`**. The trusted home root is validated and canonicalized first, so Bazzite's `/home -> /var/home` alias is supported; the printed path may therefore start with `/var/home/`. There is intentionally no arbitrary output-directory option. Keep this dedicated location separate from the game installation; do not place an installation there. Symlinks at or below the dedicated output base are rejected when traversed, including dangling links; relative paths and `..` traversal are rejected. Existing files are never overwritten. Temporary synthetic fixtures use the OS temporary directory and are removed after tests.

Reads are limited to discovered AMD DRM/hwmon nodes, selected `/proc/<pid>/stat`, `/proc/<pid>/status`, task stat/status files, and an explicitly supplied CSV. It does not search for game assets, identify a game automatically, read command lines/environments, or follow descendants. Select the Linux host PID of `nhllegacy.exe`, not Steam, Proton's launcher or wineserver. To observe another process explicitly, repeat `--pid`.

A normal game launch can write saves, caches or logs even though this tool is passive. **Game launch and any configuration changes require separate approval and an agreed test environment.** User-recorded telemetry is analyzed in [report 005](../../reports/005-simulation-vs-live-bottleneck-investigation.md); synchronized gameplay frame-time results are still unavailable.

## Output interpretation

`metadata.json` records selected PIDs, session, discovery errors, requested interval/duration and CPU clock-tick scale. `telemetry.jsonl` holds samples with UTC and host monotonic timestamps, elapsed time, collection duration, GPU sensor objects and process/thread objects. Each sensor carries its path, unit, value or error and hwmon label or label error. Zero is retained when actually read; missing/malformed/denied readings stay null. Never add labelled power channels together without knowing the power domains.

GPU discovery selects all DRM cards whose driver resolves to `amdgpu`; no silent first-GPU choice. hwmon temperature (millidegrees), frequency (Hz) and power (microwatts) are converted to C/MHz/W. Active `pp_dpm_sclk`/`pp_dpm_mclk` states are separate fields explicitly labelled **not instantaneous clocks**. Missing hwmon, utilization, clock, power and temperature data remain explicit. Sensor hotplug after initial discovery is not comprehensively handled.

`gpu_busy_percent` already has percentage units: no multiplication/division is applied. Its numeric input is preserved in utilization `raw_value`; values outside 0–100 become null with an explicit error. Values near 10000 must not be divided by 100 or clamped without evidence for that sensor/driver. Older logs retain their original values: exclude invalid utilization when analyzing them, and do not assume the remaining in-range samples validate the sensor. See [report 005](../../reports/005-simulation-vs-live-bottleneck-investigation.md).

CPU rates use deltas of `utime+stime` divided by elapsed seconds and `SC_CLK_TCK`; **100% means one logical core** and process totals can exceed 100%. Process and thread totals overlap: do not add them. Start ticks guard PID/TID identity; counter resets give null rates. Context-switch fields are cumulative counts, not latency. State is an instantaneous observation. `/proc` reads are not atomic; errors/races are retained. Spin/yield time consumes CPU, so these statistics cannot distinguish useful work from spinning or identify a GPU wait.

CSV handling accepts UTF-8/BOM, optional metadata/version preamble, comma-separated headers with `frametime` or `frametime_ms`, and quoted fields. Bare `frametime` requires `--frametime-unit ms/us/ns/s`; `frametime_ms` explicitly denotes milliseconds. Summary/FPS-only logs, absent data and repeated/duplicate headers fail clearly. Selected malformed/nonpositive/nonfinite rows are counted with line numbers, excluded from distributions, and suppress FPS. No silent FPS-to-frametime substitution occurs.

Percentiles use linear interpolation at `(n-1)*p/100`. With a validated complete per-frame stream, mean FPS is `1000 * frame_count / sum(frame_ms)`; never the mean of instantaneous FPS values. p50/p90/p95/p99 are frame-time percentiles, not “1% low FPS.” Thresholds count frames **strictly greater** than 16.67/33.33/50/100 ms; fraction means fraction of valid rows/frames, not time fraction. Small samples make p99 weak. Without `--per-frame`, the same distributions are explicitly sample statistics and FPS is null.

The importer does not infer CSV `elapsed` units/origin or automatically align frame logs with telemetry. MangoHud 0.8.4 uses elapsed nanoseconds relative to logging start, whereas telemetry uses host monotonic timestamps. Record an independent start marker for coarse correlation; precise synchronization needs future work. No tool output establishes game simulation timing, shader compilation cost, GPU timestamps or synchronization-stall duration.

### Correlation and matched 120-second runs

MangoHud elapsed starts independently at each logging toggle. Telemetry records UTC, `monotonic_ns`, relative seconds and collection duration; CPU percentages summarize differences between samples. CSV filenames have local wall-clock second resolution and cannot synchronize frames precisely. Host UTC can jump; relative monotonic clocks avoid wall-clock adjustments, but do not automatically share a known epoch with MangoHud.

Record a manually bracketed logging-start interval using the same host clock as telemetry. This read-only marker command can be run immediately before switching to the game, and again after the start toggle if practical:

```bash
python3 -c 'import time; from datetime import datetime, timezone; print(time.monotonic_ns(), datetime.now(timezone.utc).isoformat())'
```

The two markers give a **coarse bracket**, including focus/input delay; do not call it millisecond synchronization. Keep those numeric notes with the capture, outside the installation. For elapsed E ns, a frame falls approximately within `[start_before+E, start_after+E]` in host monotonic time, subject also to producer timestamp semantics. If the bracket is wide, only compare larger windows; do not associate a single long frame with a particular 0.5-second CPU sample. Sensor reads span `collection_seconds` and are not simultaneous. A future timestamped control trigger could improve alignment but is not implemented. The two old telemetry captures cannot be retroactively paired with new frames.

After a successful pilot, use new 120-second configs and `--duration 150` telemetry. Repeat three runs per workload, interleaving AI/player order to reduce thermal/order bias. Match arena, teams, camera, period length, score/period and practical match phase. Record controller input differences, stoppages/replays, AC/battery state/charge, power target and observed temperatures/clocks, display/caps/Proton identity, and telemetry/CSV paths. Label both as **rendered matches**. Reject or separately segment interruptions using known data rows; do not silently blend menus or change settings. Record normalized game-clock progression against stopwatch time on uninterrupted play; period-length rules and stoppages mean simulation timing is distinct from presentation FPS.

Reject invalid GPU utilization without clamping/dividing; MangoHud GPU load might use the same broken driver source. Keep slowPPT labelled as platform/APU-related rather than GPU-only power. CPU/thread percentages overlap. Correlation can guide CPU/GPU/stall hypotheses but cannot establish GPU execution time, useful CPU work or wait causality by itself.
